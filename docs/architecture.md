# Архитектура

## Решение: Godot 4.7.2, не Unity

Зафиксировано 2026-11-12. Причина одна: проект ведут агенты, а не человек
в редакторе.

| | Godot | Unity |
|---|---|---|
| Сцены | текст (`.tscn`) | YAML с GUID, ломается при ручной правке |
| Запуск без GUI | `--headless`, полноценно | `-batchmode`, ограниченно |
| Проверка агентом | запустил → прочитал stderr → поправил | нужен Editor, логи врозь |
| Лицензия | нет | аккаунт, Hub, активация |
| Размер проекта | мегабайты | гигабайты Library |

Unity остаётся вариантом, если появятся консоли или готовые SDK. До того — Godot.

## Структура

```
project.godot        корень проекта
scenes/              сцены (main.tscn — точка входа)
scripts/             GDScript
  hex_grid.gd        отрисовка поля и ввод (порт Hex.cs)
  main.gd            связка сцены
  rules/             правила — чистая логика, без Node2D  (создаётся)
tests/               headless-тесты правил                     (создаётся)
assets/              арты, иконки, звук
docs/                канон и память (этот файл здесь)
```

**Главное разделение:** `scripts/rules/` ничего не знает о сценах и отрисовке.
Правило воды, аура, форт — это функции над данными, которые можно вызвать
из теста без открытия окна. `hex_grid.gd` — только показывает результат.
Если правило нельзя проверить тестом, значит оно написано не там.

## Сеть: сервер-авторитет, один код правил

Пошаговая игра прощает многое: не нужен prediction, не нужен rollback.
Схема:

```
клиент (Godot)  ⇄  WebSocket  ⇄  сервер (Godot headless)  ⇄  состояние матча
```

- Сервер держит состояние и **единственный** применяет правила. Клиент присылает
  намерение («пойти A→B»), сервер отвечает результатом или отказом.
- Правила — один и тот же код на клиенте и сервере (GDScript, `scripts/rules/`).
  Клиент использует их для подсветки допустимых ходов, сервер — для проверки.
  Дублирования на второй язык нет.
- Протокол: JSON-сообщения `{type, payload, seq}`. Ход = одно сообщение,
  ответ = новое состояние + список событий (для анимаций).
- Никакого клиентского доверия: если клиент прислал недопустимый ход, сервер
  отвечает `rejected` с причиной — это же сообщение удобно показывать игроку.

Почему не готовый сервер на Node.js: пришлось бы держать правила в двух языках,
а расхождение правил на клиенте и сервере — классический источник «у меня
подсветилось, а сервер не пустил».

## Агентский цикл

```powershell
# проверить, что проект собирается
godot --headless --path . --quit

# прогнать тесты правил (когда появятся tests/)
godot --headless --path . --script res://tests/run_tests.gd

# запустить игру
godot --path .
```

Правило работы: агент не отчитывается «готово», пока не выполнил первые две
команды и не показал их вывод.
